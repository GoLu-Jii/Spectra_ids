# SPECTRA P0 SIH demo runbook

## Scope and acceptance language

This runbook demonstrates the existing P0 pipeline for DDoS and Port Scan only. Packet-path inference is **FUNCTIONALLY EXERCISED** by a controlled offline fixture. Training parity is **INCOMPLETE** and production passive-capture validation is **BLOCKED**. A successful rehearsal does not change those statuses or establish real-world detection accuracy, production throughput, or data-diode isolation.

The working baseline for this run is commit `296ff07f326756a37f424426b564fcbd4156d2e6`. The demo application uses only `P0_RUNTIME_CONFIGURATION`; C2, DNS tunnelling, and Exfiltration are not registered.

## H. Observe a WebSocket alert

The normal Uvicorn app starts REPLAY from FastAPI lifespan startup, before the server accepts HTTP/WebSocket requests. In the measured startup run, the nine alerts were created from `15:31:25.919823Z` through `15:31:26.040063Z` (120 ms). The browser's first application socket failed during startup, then opened `ws://127.0.0.1:5173/ws` at `15:31:30.870Z`, 4.829937 seconds after the last alert. It received no WebSocket messages; the visible nine-alert feed was loaded by `GET /alerts`. This is a startup race, not a queue loss.

The earlier standalone-client run received only `ALT-7587ecf6da417f57` of the nine stored IDs. The eight earlier alerts were published before that client registered; new clients are not backfilled from `AlertStore`. There were no queue drops or send failures. Queue capacity is 32, and the controlled test below observed a peak depth of 8.

For a deterministic ASGI fan-out check without changing runtime behavior, the existing test-mode app can accept `/ws` first, then invoke the existing Zeek replay reader from the verifier against the same prepared `packet.log`. That controlled run delivered all nine real alerts, matched every ID against `AlertStore`, recorded no duplicates/drops/send failures, and disconnected cleanly. It verifies the broadcaster, not the normal Uvicorn/browser startup ordering. There is no public replay trigger for the browser; a deterministic live-browser rehearsal requires an owner-approved startup/trigger mechanism. Do not count REST history as WebSocket delivery.
